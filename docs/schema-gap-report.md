# Auth & Customer schema gap report

Date: 2026-09-08

Implementation status: AUTH-DB-01 through AUTH-DB-16 were approved and implemented. AUTH-DB-15 and AUTH-DB-16 are delivered by `202609100001_generic_auth_subjects.ts`. Generic JSON redaction, retention execution, canonical identifier population, provider evidence verification, and challenge lifecycle behavior must also be enforced by the application workers built in later Auth tasks.

## Scope and evidence

This report began as a read-only review of the disposable local `parc_auth_customer` database against the pre-migration snapshot, v1 Auth & Customer contracts, and approved platform decisions. After explicit approval, the listed corrections were applied through Knex and the canonical snapshot was regenerated.

## Approved production gaps

All database changes in this section were approved and implemented. Application-level enforcement noted above remains part of subsequent Auth tasks.

| ID         | Severity | Area              | Finding                                                                                                                                                                                                                                                                                                                                   | Proposed correction                                                                                                                                                                                                                                                                                                |
| ---------- | -------- | ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| AUTH-DB-01 | Critical | KYC tiers         | `kyc_tiers` is global and mutable. It cannot represent tenant-specific, immutable published tier versions or the approved “no ceiling” Tier 3 balance.                                                                                                                                                                                    | Introduce tenant-scoped `kyc_tier_versions` with lifecycle/version fields, nullable balance ceiling, minor-unit limits, currency, requirements, publication metadata, and immutability enforcement. Reference the exact version from `customer_kyc_tiers`.                                                         |
| AUTH-DB-02 | Critical | Money             | Referral amounts use `NUMERIC(20,2)` in `referral_programs`, `referral_rewards`, and `referral_reward_transactions`, contrary to the approved posted-money representation.                                                                                                                                                                | Convert final amounts to `BIGINT` minor-unit columns, retain explicit ISO currency, validate exact conversion, and rename with `_minor` suffix.                                                                                                                                                                    |
| AUTH-DB-03 | Critical | Identity evidence | `kyc_verification_results.response_data`, verification `metadata`, AML `result_data`, and provider webhook payloads are generic JSON that could retain plaintext BVN/NIN or unsigned provider responses. `customer_documents` has encrypted/hash fields but no required masked value, key identifier, or identity-provider evidence link. | Add an explicit verification-evidence model containing masked identifier, separately keyed hash and key ID, provider reference, consent reference, result digest/signature, signing key/version, and encrypted-vault reference only when legally required. Restrict generic JSON to redacted allow-listed content. |
| AUTH-DB-04 | High     | Sessions          | `user_sessions` does not model refresh-token family, rotation sequence, replacement, reuse detection, audience, subject type, MFA/authentication strength, or absolute versus idle expiry.                                                                                                                                                | Add token-family and rotation metadata, auth context, replay-compromise timestamps, and indexes needed for atomic rotation/revocation.                                                                                                                                                                             |
| AUTH-DB-05 | High     | MFA/passkeys      | Passkey credentials exist, but persistent challenge/replay state is absent; MFA challenges are not independently modeled. Redis may hold short-lived challenges, but durable audit/replay evidence is still required.                                                                                                                     | Add purpose-bound authentication challenge records or explicitly approve Redis-only challenge state plus durable consumed-result audit records.                                                                                                                                                                    |
| AUTH-DB-06 | High     | Tenant isolation  | RLS is forced on tenant tables, but policies target `PUBLIC`, several tables have duplicate permissive policies, and roles are generic platform roles rather than Auth-specific least-privilege roles. The inspection login is a superuser and bypasses RLS.                                                                              | Remove duplicate policies, bind policies/grants to Auth runtime/worker/migration/read-only roles, prohibit runtime ownership or `BYPASSRLS`, and add owner-bypass integration tests.                                                                                                                               |
| AUTH-DB-07 | High     | Retention         | Tables carry timestamps but no explicit retention classification, purge eligibility, legal-hold marker, or archival workflow for the approved 30-day/90-day/24-month/5-year/7-year schedules.                                                                                                                                             | Add retention policy documentation and only the minimum columns/indexes needed for legal hold and scheduled purge/archive workers.                                                                                                                                                                                 |
| AUTH-DB-08 | High     | Admin boundary    | `user_type` includes `STAFF`, although administrator identity is owned by Tenant Admin and Auth only issues JWTs after synchronous verification.                                                                                                                                                                                          | Prevent new Auth-local staff identities and define a compatibility path for any existing `STAFF` rows; retain only customer and service-subject concepts needed by Auth.                                                                                                                                           |
| AUTH-DB-09 | Medium   | Notifications     | `notifications` retains recipient, subject, and full body without a classification or `retain_until`; this cannot safely enforce the approved content and metadata retention differences.                                                                                                                                                 | Add classification, content expiry, metadata expiry, and legal-hold fields; purge message content independently of delivery metadata.                                                                                                                                                                              |
| AUTH-DB-10 | Medium   | Consent           | Consent records capture type, document version, IP, user agent, and time, but do not explicitly capture purpose, channel, evidence digest, or policy URI.                                                                                                                                                                                 | Extend consent evidence without overwriting historical consent rows.                                                                                                                                                                                                                                               |
| AUTH-DB-11 | Medium   | Identifiers       | Phone values lack a canonical E.164 constraint/normalized column. Email uniqueness uses `lower(email)` but canonicalization behavior is not documented.                                                                                                                                                                                   | Store canonical identifiers, preserve display values only where needed, and keep uniqueness tenant-scoped.                                                                                                                                                                                                         |
| AUTH-DB-12 | Medium   | Audit integrity   | Auth audit events allow ordinary update/delete because immutability is not enforced at the database role/trigger level. Previous/new JSON may accidentally contain secrets.                                                                                                                                                               | Make audit rows append-only for runtime roles and enforce a redacted schema at the application boundary.                                                                                                                                                                                                           |
| AUTH-DB-13 | Medium   | Provider routing  | Verification rows store provider names, but do not record the Tenant Admin provider-selection/configuration version used for the request.                                                                                                                                                                                                 | Record provider selection/config version and request attempt metadata so outcomes are reproducible.                                                                                                                                                                                                                |
| AUTH-DB-14 | Medium   | Migration history | There is no executable migration baseline or recorded baseline procedure.                                                                                                                                                                                                                                                                 | Establish the synchronized snapshot as migration `0001`, then apply every approved correction as a separate forward migration.                                                                                                                                                                                     |
| AUTH-DB-15 | Critical | Auth ownership    | Customer-only foreign keys prevented Auth-owned sessions, MFA methods, and challenges from safely referencing administrator identities owned by Tenant Admin.                                                                                                                                                                             | Add generic subject identity/type columns while retaining a nullable local-customer foreign key and database checks that prohibit administrators from masquerading as customers.                                                                                                                                   |
| AUTH-DB-16 | Critical | Platform scope    | Platform administrators have no tenant, while all authentication state required a tenant identifier.                                                                                                                                                                                                                                      | Add explicit `TENANT`/`PLATFORM` scope, allow null tenant IDs only for platform administrators, and restrict tenantless rows through platform-scoped RLS context.                                                                                                                                                  |

## Contract coverage conclusion

The existing schema substantially covers registration, customer profiles, passwords, PINs, OTP, sessions, MFA methods, passkeys, KYC workflow, consent, devices, notifications, idempotency, inbox/outbox, fraud, and audit. It is not yet production-ready for the approved contract because AUTH-DB-01 through AUTH-DB-08 affect core security, financial correctness, identity-data minimization, or bounded-service ownership.
